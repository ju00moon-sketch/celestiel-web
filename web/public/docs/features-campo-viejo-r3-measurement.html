R3 — 캄포 비에호 패키지 성능 측정 준비

2026-09-28, ⑤. 기준: campo-viejo-render-plan.md §4.2와 총괄의 R3 준비 배정. ②-A의 UE5.8.3 소스 확인에 따른 총괄 결정으로 P1 카메라 진단 재생 → P1 검토 → P2 의미 단위 흐름 A로 연결 계약을 나눈다. P1 구현 대조 후 승인된 반복 전 안정화·내부 픽셀 유도값·IgnoreFocus와 오프라인 판정 규칙을 추가 반영했다. 이번 갱신은 문서와 판정 도구/회귀 검사이며 런타임 구현·패키지·60fps 통과 보고가 아니다. Unreal·빌드·맵 저장·설정 변경·커밋은 하지 않는다.

목표는 다음 Development 패키지에서 실제 흐름 A의 기본 품질·출력 1920×1080 평균 프레임 시간이 16.7ms 이하인지 판단할 자료를 준비하는 것이다. 1000/60=16.666…ms는 P95 및 초과 프레임 조정 목표로 따로 쓴다. CPU·GPU 시간을 합산하거나 FPS 평균을 내지 않는다.

준비 작업과 경계

  1. Scripts/TechArt/prepare_campo_render_r3.py: V01~V09 원본과 지형 GLB를 읽어 실제 월드 cm 좌표의 180초 진단 카메라 JSON을 만든다. 절대 시간 재생, 컷, 보간, 원본 해시와 미검증 상태를 명시한다. 출력은 새 Saved 폴더만 사용한다.
  2. Scripts/TechArt/assess_campo_render_r3.py: CSV의 반복 BEGIN/END 마커 사이 전체 프레임을 분석하고 평균 16.7ms·P95·hitch·CPU/GPU와 근거 누락을 판정한다. 기존 summarize_campo_render_csv.py의 통계/CSV 판독을 재사용한다.
  3. Scripts/TechArt/tests/test_campo_render_r3.py: 긴 측정 경계 프레임, 꼬리 부족, 결측 GPU, 반복 누락, 16.7ms 경계, 카메라 컷·각도·시간 독립성과 출력 묶음 보호를 오프라인으로 검사한다.

게임 코드와 Scripts/Level은 ⑤가 수정하지 않는다. 기존 Celestiel.Explore.WalkPath는 도달/막힘 기반이며 고정 카메라 재생기나 실제 흐름 A 벤치마크가 아니다. ②가 구현할 런타임 계약은 아래에 둔다. 엔진 Python을 패키지에서 사용할 수 있다고 가정하지 않는다.

측정 구간

V01~V09는 서로 다른 초기 상태의 검증 경로다. 순서대로 이어 붙여 전투를 끄거나 완료 플래그를 건너뛴 결과를 흐름 A로 부르지 않는다.

이 카메라 순회는 P1 환경 진단용이다. B01~B04의 고정 구도만으로 공격·대응·UI·전환 부하가 측정되지는 않는다. P1은 flow_a를 NOT_READY로 거부한다. P2는 celestiel.cv.flow/1 의미 단위 어댑터가 걷기 경로점·전투 기록·확인·복귀 단계를 진행한다. 준비 런의 RecordFlow가 PCM의 최종 월드 transform/FOV/cut와 단계 시각을 flow_a 카메라 JSON으로 기록한다. 측정 반복에서는 게임 카메라를 그대로 두고 이 기록과 비교만 한다. 원시 키 입력 재생이나 기준 카메라 궤적의 강제 적용은 하지 않는다. 진단 순회의 180초로 실제 전투 시간을 늘이거나 줄이지 않는다.

지형 높이는 기존 경로 JSON의 누락 z를 0으로 채우지 않고 terrain_manifest.json의 원본 GLB 삼각형 면에서 계산한다. 사람 시점은 해당 위치의 면+170cm이며 실제 플레이어 SpringArm 카메라와 구별한다. 공터 조망은 ⑥의 현재 궤도 식을 수치로 기록한다. 원본 JSON과 소스/맵 해시가 달라지면 다시 동결한다. 런타임에서 실제 지면·가림·컷·최종 ViewRect를 확인하기 전에는 경로를 검증 완료로 표시하지 않는다.

준비 도구 사용

아래 두 Python 도구는 엔진을 띄우지 않는다. 새 출력 폴더만 사용한다. camera_path.json, commands.json, evidence.template.json이 하나의 묶음이며 폴더가 이미 있으면 어느 파일도 덮어쓰지 않는다.


py -B Scripts/TechArt/prepare_campo_render_r3.py --terrain-manifest (내부 경로) --output (내부 경로)
py -B -m unittest discover -s Scripts/TechArt/tests -p 'test_campo_render*.py' -v

P1 camera_path.json의 keyframes는 t(초), location(월드 cm XYZ), rotation(pitch/yaw/roll 도), 수평 fov, cut이다. 시간은 처음0·마지막duration을 포함하고 엄격히 증가한다. 위치/FOV 선형, 각도는 짧은 호로 보간한다. 다음 키가 cut이면 그 시각 전까지 앞 키를 유지한다. 반복마다 기준점을 새로 잡고, pose·컷·END는 BEGIN 다음 프레임부터 FApp 프레임 간격을 CSV 기록 정밀도(float·소수4자리 ms)로 반올림한 한 누적으로 정한다. 실제 CSV FrameTime과의 일치는 쓰기 완료 뒤 자체 판독으로 검증한다. 반올림 전 FApp 총경과는 아래 마커 계약의 참고값이며 별도 END 판정 시계로 쓰지 않는다. 별도 tick delta 누적기나 고정 시간 간격으로 진행하지 않는다. 실제 컷은 렌더러에 알려 TAA/Lumen 이력을 재사용하지 않게 한다. source_sha256는 레벨·지형·경로의 현재 스냅샷이며 패키지 manifest와 대조한다. P2의 같은 모양의 카메라 자료는 비교 기준이고 뷰 타깃을 구동하지 않는다.

다음 패키지에서 실행할 순서와 명령

실행권을 받은 뒤에만 사용한다. 다음 패키지의 실제 Development EXE·커밋·Cook manifest가 있어야 한다. 기존 에디터/프로젝트 Python을 패키지에서 실행하지 않는다. 아래는 명령의 인자 계약이고 이번 준비에서는 실행하지 않았다.

  1. 패키지·카메라 JSON·맵/조명/물 재질 해시를 고정한다. P2에서는 의미 단위 flow JSON·전투 기록·초기 상태 식별자도 묶어 고정한다. 빌드 구성, PC/GPU·드라이버·전원/클럭·VRAM, 초기 품질 sg.*·DeviceProfile·GameUserSettings를 기록한다. 현재 조명 A·물 재질 수용값을 사용하고 원본 품질·sg.*·텍스처 해상도를 낮추지 않는다. 패키지 시작 전 사용 가능 RAM 10GiB 이상을 확인한다.
  2. 출력/내부 해상도 목표는 1920×1080, TSR100%, DynamicRes OFF, VSync OFF, 프레임 제한0이다. 게임 스레드에서 실제 렌더 ViewRect를 바로 읽지 못하므로 internal_pixels는 뷰포트의 각 축 × r.ScreenPercentage/100 유도값으로 기록한다. 반드시 '유도값, 최종 ViewRect는 런타임 로그로 확인'이라고 표시하고 뷰포트·ScreenPercentage 근거를 함께 남긴다. 창 크기 인자나 유도값만으로 실제 내부 해상도를 확인했다고 하지 않는다. 최종 ViewRect·렌더 크기·레터박스 여부는 런타임 로그로 대조한다. 성능 런의 기본 PP는 유지하고 비교 캡처용 PP 변경을 섞지 않는다. 패키지 성능 실행은 Celestiel.RenderProbe.IgnoreFocus=0 고정이다.

# 예시: 경로와 로그 폴더를 다음 패키지/새 런에 맞춘 뒤 실행권 배정 후 사용.
& '<Development 패키지 EXE 절대 경로>' '/Game/Maps/L_CampoViejo_Blockout' '-windowed' '-ResX=1920' '-ResY=1080' '-NoVSync' '-csvGpuStats' '-csvCompression=0' '-log' '-abslog=<별도 로그 폴더>/R3_<실행ID>.log' '-DisablePlugins=ModelContextProtocol,ToolsetRegistry,EditorToolset,UMGToolSet,AutomationTestToolset' '-ExecCmds=r.VSync 0,t.MaxFPS 0,r.AntiAliasingMethod 4,r.ScreenPercentage 100,r.DynamicRes.OperationMode 0,Celestiel.RenderProbe.IgnoreFocus 0'

로그는 Play 출력과 다른 폴더에 둔다. Play가 만들 근거 폴더를 미리 생성하거나 -abslog가 먼저 만들게 하면 OUTPUT_EXISTS로 거부된다.

  1. 최초 진입의 로딩/PSO/스트리밍 hitch는 별도 COLD 자료로 보존한다. 캐시를 지우거나 첫 실행이 없었던 것처럼 재기록하지 않는다. 정상 맵 준비 뒤 최소30초 경과 AND 비동기 로딩 남은 수0 AND PSO 남은 수0를 모두 기다린다. 실제 대기 초·확인한 남은 수를 기록하고, 30초가 지났다는 이유만으로 진행하지 않는다. 최고 mip 상주/스트리밍 검증은 별도 근거로 유지한다. P1은 최초 안정화 → 같은 경로 예열1회 → 각 반복 전 첫 pose 안정화 → R01~R03이다. 반복 전 대기는 아래 계약대로 첫 pose 최소2초 + 비동기 로딩 없음 + PSO 남은 수0이며 측정 밖이다.
  2. P1 카메라 진단180초로 외형·컷·경계/예배당 시점을 확인하고 CSV 마커·쓰기·복구를 검토한다. 그 검토 뒤 P2를 연결한다. P2 준비 런은 RecordFlow로 진입→마을 관찰→공터 전투(조망·행동·대응·효과/UI)→확인·탐험 복귀→출구/끝 화면의 의미 단계를 실행·기록한다. 전투 중 규칙 시간을 강제로 진행하거나 트리거를 끄지 않는다. 최종 PCM 기록이 유효한지 확인한 뒤 suite=flow_a 기준 자료로 사용한다. 현재 진단 JSON의 suite만 바꾸어 실제 흐름 A 자료처럼 만들지 않는다.
  3. 각 suite의 같은 승인 입력을 R01~R03 세 번 실행한다. P2는 반복 사이 맵 다시 열기와 매 반복의 안정화 조건 대기를 측정 밖에서 수행하며 같은 초기 상태·flow/전투 기록 SHA를 확인한다. 측정 중에는 게임 카메라에 개입하지 않는다. 전투 진입·복귀·컷 프레임과 hitch는 모두 포함한다. 입력 대기 시간을 늘이거나 끝 화면을 붙잡아 평균을 낮추지 않는다. 외부 입력·포커스 상실·의도하지 않은 정지는 보존·실패 처리한다. P2의 의미 단계 완료 시각과 현재 고정D CSV 도구의 대응은 아래 P2 검증 항목에서 확정한다.

승인된 Play 실행기가 아래 순서를 소유한다. 수동 스모크도 같은 순서를 지키고 ExecCmds에 전부 붙여 시간이 흘렀다고 간주하지 않는다. 운영자가 Play와 수동 CSV 명령을 동시에 돌리지 않는다.


csvprofile STARTFILE=R3_<실행ID>_R01.csv
csvprofile START
<캡처 활성 1프레임 확인 → BEGIN → 재생 → END>
csvprofile STOP
<비동기 쓰기 완료 확인 → 새 근거 폴더에 복사 → SHA256 확인>

STARTFILE은 이름만 지정하고 캡처를 시작하지 않는다. 로컬 UE5.8.3 Engine/Source/Runtime/Core/Private/ProfilingDebugging/CsvProfiler.cpp의 CsvProfileCommand(1051), 출력 경로/압축 처리(3953~), GetDefaultDirectory(4739), csvGpuStats(5098)에서 확인했다. 기본 출력은 해당 패키지 (내부 경로) -csvCompression=0으로 일반 CSV를 요청한다. STOP 직후 종료하지 말고 CSV 쓰기 완료 로그·파일 완료를 확인한 뒤 프로젝트의 새 Saved 런 폴더로 복사하고 SHA를 기록한다. csvprofile FRAMES=N/-csvCaptureFrames는 fps에 따라 시간이 달라지거나 부팅을 섞으므로 이번 시간 기반 측정에 쓰지 않는다.

  1. 해상도·카메라·UI 캡처는 동일 경로의 별도 외형 런에서 만든다. 측정 중 HighResShot·GPU Visualizer·상세 Insights·화면 녹화를 돌리지 않는다. 필요한 병목 장면에만 별도 trace/GPU 패스 캡처를 실행한다. stat 화면은 진단 참고값이며 판정의 원시 CSV를 대신하지 않는다.
  2. 새 근거 JSON은 template을 복사해 실제 값으로 채우고, run_id(status와 같은 실행 식별자)·focus_check(불리언)를 추가한다. 과거 bundle02 템플릿에 없는 칸도 실제 런의 값으로 명시하며 파일이 오래됐다는 이유로 포커스 확인을 생략하지 않는다. focus_check=false이면 성능 근거로 쓰지 않는다. artifacts는 패키지 manifest, runtime_log, 최종 camera_trace, quality_snapshot, memory, gameplay_proof의 경로/SHA를 요구한다. 경로는 evidence 파일 기준 상대 경로나 절대 경로다. checks는 실제 검증 뒤에만 true로 쓴다. 템플릿의 null/false는 통과할 수 없다. --list-columns로 CSV 실제 열을 읽고 Frame/Game/Render/GPU의 서로 다른 ms 열을 지정한다. GT/RT/GPU 누락·NaN·0은 오류로 처리하며 FrameTime을 복사해서 채우지 않는다.

py -B Scripts/TechArt/summarize_campo_render_csv.py '<R01 CSV>' --list-columns
py -B Scripts/TechArt/assess_campo_render_r3.py --route '<검증된 camera_path.json>' --evidence '<근거 JSON>' --output (내부 경로)

현재 판정 스크립트는 eligible_for_review일 때만 종료0, 진단 전용·근거 누락·예산 초과는 JSON을 남기고 종료2다. P1의 diagnostic_only/종료2는 실제 흐름 A 성능 합격을 주장하지 않는 정상 분류이며 CSV 실행 오류와 구별한다. 입력/마커 오류는 예외 종료하며 성공 JSON을 쓰지 않는다. 각 반복의 평균≤16.7ms가 모두 필요하고 합산 평균으로 느린 반복을 가리지 않는다. 평균/중앙값/P95/P99/최대, 16.666…/16.7/33.333…ms 초과, Game/Render/GPU ms를 기록한다. P95 목표 미달·hitch는 평균 통과와 별도로 보고한다. 스크립트는 근거 파일 존재/SHA와 선언한 실행 조건을 검사할 뿐, 사진의 품질이나 카메라 trace 내용까지 자동으로 보증하지 않는다. 총괄/③의 근거 검토가 남는다. P2 적용은 아래 고정D 가정 대조가 끝난 뒤이며 이번 포커스 조건 수정으로 P2 시간 판정 지원까지 검증한 것은 아니다.

assess_campo_render_r3.py는 focus_check가 명시적인 불리언 true일 때만 포커스 조건을 충족한 것으로 처리한다. false·누락·null·문자열/숫자는 missing_evidence에 focus_check를 남기며, flow_a는 insufficient_evidence/종료2가 된다. camera_diagnostic은 기존 diagnostic_only 분류를 유지하고 어느 경우든 eligible_for_review가 아니다. run_id는 추적용 메타데이터로 두며, 그 외 모르는 칸을 추가했다는 이유만으로 거부하지 않는다.

CSV 중복 이름은 EVENTS와 실제 판정에 선택한 evidence.columns 열에서만 거부하며, 사용하지 않는 중복 이름은 ignored_duplicate_columns로 판독 통계·반복별 판정 결과·evidence의 각 repeat에 기록한다. read_capture(path, columns)에 선택 열 매핑을 넘기고, 매핑 없이 머리글만 볼 때는 EVENTS/FrameTime을 보호한다. R3 판정 출력의 evidence는 이 목록을 추가한 사본이며 evidence_sha256은 변경하지 않은 입력 evidence 파일의 해시다. 원본 CSV와 입력 evidence 파일은 덮어쓰거나 중복 열을 삭제·개명하지 않는다. 런타임 evidence 생성 측도 같은 반복별 필드를 사용한다.

열 이름 탐색과 중복 이름 비교는 런타임·판독기 모두 대소문자 구별(CaseSensitive)이다. FrameTime과 frametime은 다른 열이며, evidence.columns에는 실제 머리글과 정확히 같은 이름을 쓴다.

P1 실행 suite는 camera_diagnostic 하나다. 시작이 수락되면 즉시 [CVR3] ACCEPTED <run_id>를 남긴다. run_id는 새 출력 폴더의 마지막 이름이다. 비동기 명령이므로 이 로그나 프로세스 종료0은 측정 성공이 아니다. Play 한 번이 안정화·예열1회·세 반복·정리까지 소유하며 운영자가 같은 명령을 세 번 호출하지 않는다.

P1 안정화·반복·마커 시각

최초 안정화는 최소30초 경과 + 비동기 로딩 남은 수0 + PSO 남은 수0의 세 조건을 동시에 만족할 때 끝난다. measurement.warmup_seconds_min이30보다 크면 그 값을 하한으로 쓴다. 실제 기다린 초, 두 준비 조건의 관측값과 확인 시점을 남긴다. 관측할 수 없는 값을 임의로0으로 기록하지 않는다.

예열1회가 끝난 뒤와 각 반복 R01/R02/R03 직전에는 경로의 첫 pose로 돌아가 첫 pose가 실제 적용된 프레임부터 최소2초 + 비동기 로딩 없음 + PSO 남은 수0를 동시에 만족할 때까지 멈춘다. 첫 pose 적용 요청을 보낸 시점부터 세지 않는다. 예열 직후의 대기가 before_R01이고 다음 반복 전 대기는 before_R02, before_R03이므로 R01 앞에서 두 번 중복 대기하라는 뜻은 아니다. 경로 끝에서 시작점으로 건너뛴 직후의 스트리밍 조건을 반복마다 맞추기 위한 절차다. 모두 측정 밖·CSV BEGIN 이전이며, 최초30초 안정화를 대체하지 않는다. status.stabilizations에 위 식별자와 실제 대기 초·관측 조건을 기록한다.

각 반복은 첫 pose 안정화(before_R0n) → CSV 시작 → 캡처가 활성인 1프레임 확인 → BEGIN → 경로 재생 → END → STOP → 비동기 쓰기 완료 → 복사·SHA256 순이다. CSV 파일명은 R3_<run_id>_R01.csv부터 R03까지 분리한다. 앞 반복의 쓰기가 끝나기 전에 다음 CSV를 시작하지 않는다. 마커 밖 준비·flush 프레임은 성능 평균에 넣지 않는다.

②-A의 UE5.8.3 소스 확인에 따라 CSV FrameTime은 FCsvProfiler::UpdateFrameTime이 UpdateTimeAndHandleMaxTickRate 직후 FPlatformTime::Seconds()로 따로 잰 간격이다(CsvProfiler.cpp 4369~4390행, LaunchEngineLoop.cpp 5698~5705행). FApp 간격 자체가 아니며, 그 기록값을 런타임이 읽는 공개 API는 없다. 행 N은 프레임 N의 델타이며 한 행 늦은 값으로 취급하지 않는다. 실측 차이는 표본 시점 간격(중앙0.6~15µs, 99% ≤16.5µs, 한 프레임 최대0.19ms)으로 누적 표류가 아니다.

  1. BEGIN 프레임에서 런타임의 반올림 간격 누적을0으로 시작하고, 참고용 시작 시각 T0 = FApp::GetCurrentTime()을 남긴 뒤 같은 프레임 안에서 CSV_EVENT_GLOBAL로 BEGIN을 기록한다. BEGIN 행의 델타는 T0 이전 구간이므로 누적과 통계에서 제외한다.
  2. 런타임은 FApp 프레임 간격을 CSV 기록 정밀도(float·소수4자리 ms)로 반올림해 누적하고, 이 한 누적으로 pose·컷·END를 정한다. 실제 기록값은 엔진이 따로 재어 런타임이 읽을 수 없으며, 차이는 표본 시점 간격(µs, 드물게0.2ms)이다. END가 어긋나면 자체 판독이 CSV_ERROR로 잡는다. 누적 ms를1000으로 나눠 경과 초를 구하며, UseFixedTimeStep·시간 배속·별도 tick delta 누적기로 바꾸지 않는다.
  3. 위 런타임 누적 경과가 D 이상이 되는 첫 프레임 안에서 마지막 pose를 처리하고 CSV_EVENT_GLOBAL로 END를 남긴다. 다음 유휴 프레임으로 미루지 않는다. 최종 pose 평가만 D로 제한하며 통계의 마지막 긴 델타는 잘라내지 않는다. 반올림 전 FApp 총경과로 END를 앞당기지 않는다. 실제 CSV로 계산한 END 행과의 일치는 쓰기 완료 뒤 반드시 자체 판독한다.
  4. RecordEventAtTimestamp는 ContinuousWrites와 충돌한다는 경고가 있어 사용하지 않는다. 마커 시각을 사후 보정해 맞추지 않는다.

예열 구간은 CSV를 기록하지 않으므로 FApp 경과를 그대로 사용한다. 측정 반복의 반올림 누적과 구별한다.

END 프레임의 FApp::GetCurrentTime() - T0는 참고값 fapp_elapsed_at_end_s로 evidence·status에 반복별로 기록한다. CSV 쓰기 완료 뒤 런타임 자체 판독은 실제 기록값의 합 csv_elapsed_s = FrameTime 누적 ms / 1000을 구하고, abs(fapp_elapsed_at_end_s - csv_elapsed_s) <= END 행 FrameTime_ms / 1000을 확인한다. 차이가 END 행의 FrameTime보다 크면 CSV_ERROR로 실패 처리한다. 단위를 초로 맞춰 비교하며 FApp 값을 CSV 합에 보정해 더하지 않는다. 이 기준은 CSV만으로 END를 검증하기 위한 결정이다. 예를 들어 D=60초, 프레임 델타60.0001/7200초일 때 FApp 경과60.0001초여도 실제 CSV 기록값의 합이59.99976초라면 그 행의 END는 자체 판독에서 실패한다.

CSV 이벤트 첫 번째 열의 정확한 토큰은 다음 여섯 개다. 통계 열 이름이나 일반 로그로 대체하지 않는다.


[CVR3_R01_BEGIN]  [CVR3_R01_END]
[CVR3_R02_BEGIN]  [CVR3_R02_END]
[CVR3_R03_BEGIN]  [CVR3_R03_END]

BEGIN 행 제외·END 행 포함을 유지한다. 반복마다 각 토큰이 정확히1개여야 하며 진행 로그를 CSV 이벤트에 복제하지 않는다. 채택 행의 FrameTime 합이 D를 처음 채우는 행이 END여야 한다. 긴 BEGIN 행, 마지막 hitch, 꼬리 부족, END가 한 행 늦은 경우를 짧은 패키지 스모크와 판정 도구로 대조한다. Frame/Game/Render/GPU는 실제 서로 다른 ms 열 이름을 evidence.json.columns에 쓴다.

스모크의 엄격 기준은 BEGIN/END 행 맞춤·컷 행·마지막 pose가 실제 CSV로 계산한 행과 같은 것이다. 별도 온전성 기준은 pose 시각 차이의 99%가1ms 이하인 것이다. 온전성 기준을 만족해도 엄격 기준의 행 불일치를 허용하지 않는다.

진단 카메라만 임시 뷰 타깃으로 구동한다. 요청 pose와 최종 PCM pose/FOV/cut·뷰포트 크기·ScreenPercentage를 함께 기록한다. internal pixels는 유도값이며 최종 ViewRect 실측이 아니다. evidence·quality_snapshot에 이 출처를 명시하고 실제 렌더 영역 확인은 런타임 로그 근거를 연결한다. cut=true 시각을 프레임이 건너도 컷을 한 번 처리해 SetGameCameraCutThisFrame으로 렌더러에 알린다. 위치/각도 허용 오차는 첫 스모크의 기록 지연을 확인해 정하며 조용히 넓히지 않는다. 30/60/120fps의 같은 경과 시각 pose 비교는 재생기 단위 검사이고, 실제120fps 성능 달성과 구별한다.

무인 스모크 포커스 예외

콘솔 변수 Celestiel.RenderProbe.IgnoreFocus는 기본0이다. 0에서는 포커스를 잃으면 기존 FOCUS_LOST로 중단한다. 1은 무인 스모크 전용으로 포커스가 없는 프레임 수를 세면서 진행하고 그 사유만으로 FOCUS_LOST 종료하지 않는다. status·evidence·quality_snapshot 세 곳에 focus_check=false를 남긴다. 포커스 없는 프레임 수가0이어도 검사를 우회한 런이면 false이며, 중간에0으로 되돌렸다는 이유로 이미 우회한 런을 true로 바꾸지 않는다. 측정·오류 진단 근거로 보존할 수 있지만 성능 검토 가능 결과로 쓰지 않는다. 패키지 성능 실행은0 고정이고 focus_check=true 근거가 필요하다. 다른 중단 조건과 부분 파일 보존/복구는 그대로 적용한다.

SHA256·완료·실패·복구

FPlatformMisc::GetSHA256Signature는 Windows 미구현이므로 이 API로 성공을 가정하지 않는다. ②-A가 진단 모듈 안에 자체 SHA-256을 구현하고 NIST 알려진 답 벡터로 빈 입력·짧은 입력·여러 블록을 검사한다. 최종 파일의 해시는 외부 오프라인 SHA256과도 대조한다. 새 라이브러리 설치나 네트워크 조회는 필요하지 않다. 완료된 CSV를 복사한 뒤 원본/사본의 SHA가 같은지 확인하며 복사/해시 실패를 완료로 처리하지 않는다.

status.json은 schema="celestiel.cv.run/1", run_id, state, reason, route_sha256, completed_repeats, csv_flushed, restored_camera_and_input, stabilizations, focus_check와 포커스 없는 프레임 수를 기록한다. 상태는 accepted/running/completed/failed로 구별하고, 안정화 실측과 반복별 쓰기/복사·SHA 결과를 근거에 연결한다. 정상 완료는 세 반복의 올바른 END, 세 CSV 쓰기 완료·복사·SHA 일치, 필요한 근거 쓰기, 카메라/입력 복구를 모두 확인한 뒤에만 state="completed", reason="OK", [CVR3] COMPLETE <run_id>로 기록한다. 완료 카운터만3이라는 이유로 통과시키지 않는다. IgnoreFocus=1 스모크의 실행 완료도 가능하지만 focus_check=false이므로 성능 근거로 승격하지 않는다.

출력은 evidence.json(celestiel.cv.measurement/1), 반복 CSV, camera_trace.jsonl, quality_snapshot.json, gameplay_proof.json이다. 외부 감시 memory.json, 패키지 manifest/runtime log는 경로·SHA를 연결한다. 없거나 확인하지 못한 근거는 false/null로 남겨 성능 판정을 막는다. P1의 gameplay proof는 진단 범위임을 적고 gameplay_verified=true로 꾸미지 않는다. completed는 실행 수명 종료이며 실제 흐름 A·60fps 합격은 별도다.

P2 의미 단위 흐름 A와 RecordFlow

P2는 P1 검토 통과 뒤 구현한다. 어댑터 schema는 celestiel.cv.flow/1, 내용은 걷기 경로점·전투 기록·확인 및 탐험 복귀 단계다. 탐험 이동/완료 판단은②-B, 묶음/전투/측정은②-A가 소유한다. 원시 키 입력 재생은 사용하지 않고 정상 게임 흐름을 호출하며 규칙/사건 결과를 검사한다.

준비 런 명령과 인자 계약안은 다음과 같다. RecordFlow의 두 인자 형식과 아래 연결 필드명은 이 문서의 P2 초안이며 ②-A/②-B가 의미 단계 schema를 고정할 때 함께 대조한다. 총괄이 승인한 명령 이름·기록 목적·관찰 전용 카메라 원칙은 바꾸지 않는다.

RecordFlow 입력은 UTF-8 celestiel.cv.flow/1 JSON과 아직 존재하지 않는 Saved 출력 폴더다. 초기 상태·맵/입력 해시·어댑터 준비를 사전 검사하고 같은 BUSY/INVALID_INPUT/OUTPUT_EXISTS/NOT_READY 원칙을 적용한다. 준비 런의 실제 최종 PCM transform/FOV/cut·단계 식별자/시각·전투 결과·복귀 완료를 기록해 suite=flow_a 카메라 JSON을 만든다. 기준 길이와 샘플 시각은 실제 기록에서 얻는다. 입력 경로나 카메라 파일을 덮어쓰지 않는다. 기록 완료는 성능 측정 완료가 아니며 검증하지 않은 자료를 runtime_validated=true로 쓰지 않는다.

P2 카메라 JSON에는 flow_a.contract={path,sha256}로 의미 단위 flow 원본을, flow_a.initial_state_id로 초기 상태를 연결하는 안을 사용한다. 종속 전투 기록도 경로·SHA로 묶는다. 경로는 입력 JSON 기준 상대 경로나 절대 경로다. 걷기 도달/전투 기록/확인·복귀의 세부 step 키·완료 조건은 양 구현 담당의 P2 인계에서 고정한다. 기존 진단 JSON의 suite만 바꾸거나 원시 입력 로그를 연결해 대신 실행하지 않는다.

P2 판정 연결 시 남은 대조: 현재 assess_campo_render_r3.py는 세 반복 모두 카메라 JSON의 같은 D를 사용해 채택 시간≥D, END 이전 합<D를 검사한다. 의미 단위 실행의 완료 시각이 반복마다 달라질 수 있으므로 이 가정을 P2에 그대로 적용할 수 있다고 주장하지 않는다. P2 구현 전에 ②-A가 의미 단계 시작/끝·허용 시간 차·실측 길이 기록을 고정하고, ⑤는 BEGIN 제외/END 포함과 반복별 실제 구간을 판정 도구에 대조한다. 길이를 맞추려고 게임 카메라·규칙 시간을 강제하거나 끝 화면 대기를 덧붙이지 않는다. 반복별 구간이 달라지면 별도 판정 도구 수정·회귀 검토가 필요하다. 이번 포커스 검사는 이 시간 구간 판정을 바꾸지 않으며 기존 도구의 P2 지원 완료를 보고하지 않는다.
