반응형 전투 M1 — 기술 설계와 작업 단위

  • 작성: ① 총괄, 2026-09-24
  • 규칙 기준: combat-reactive-prototype.md(RT-v0.3+D8). 수치: docs/BALANCE_LOG.md(A3-v0.2).
  • 목표: 규칙 핵심을 엔진 화면 없이 실행·재현·자동 시험할 수 있게 만든다. 첫 사용자 보고는 성공·일부 성공·무입력·A 사망 사례의 재현 로그와 테스트 결과다.
  • MCP: 쓰지 않는다(Unreal MCP는 라이선스 확인 전 보류). 빌드와 자동 테스트는 docs/VERIFICATION.md 3절 명령으로 한다.

1. 구조 경계 (RT-11)

층책임단계
규칙 핵심상태, 피해·보호막·집중력, 승패, 릴레이 생성·소비, 예약 유효성M1
명령·입력계획 데이터와 검증, 예약 후보, 정밀 입력 사건, 예약 선택M1(입력은 주입)
공격 일정예고·입력창·타격·공격 종료·결정 지점 사건, 전투 시계M1
기록·재실행사건 로그, 입력 로그 저장과 재실행, 조건부 미리보기M1
표시·연출UI, 임시 동작, 카메라, 실제 키 입력 연결M2
  • 규칙 핵심은 UWorld·틱·렌더링·UObject 수명에 의존하지 않는 C++로 만든다. M2의 게임 쪽(액터·서브시스템·위젯)은 핵심을 호출하고 사건을 구독만 한다. 표시 쪽이 규칙 결과를 계산하거나 바꾸지 않는다.
  • 위치: Source/Celestiel/Combat/(핵심), Source/Celestiel/Tests/Combat/(자동 테스트). 세부 클래스·파일 구성은 ②가 정한다. 공유 인터페이스(아래 4·5절)를 바꿔야 하면 총괄과 먼저 조율한다.
  • 규칙에 들어가는 외부 입력은 세 가지다: 계획, 정밀 방어 누름(공격 기준 시각), 예약 선택. 난수·실제 시각·프레임 수는 규칙에 들어가지 않는다.

2. 결정성 규칙

  • 체력·피해·집중력·시각은 정수다. 시각은 그 라운드 보스 공격 시작 기준 활성 전투 시간(ms)이다.
  • 율은 1/10000 정수(기본 방어 4000, 정밀 추가 2500)로 두고, 타격 피해 = (기본 × (10000 − 방어) × (10000 − 정밀)) ÷ 10000²을 64비트 정수 나눗셈(내림)으로 한 번 계산한다. 40이면 무입력 24, 성공 18.
  • 부동소수, 난수, 실제 시각, TMap 순회 순서를 결과나 로그에 쓰지 않는다. 인물은 A~E 고정 순서로 둔다.
  • 같은 시각의 처리 순서는 예고 시작 → 누름(제출 순서) → 타격 판정·피해 → 공격 종료다(4절).
  • 버전 문자열(규칙 RT-v0.3+D8, 수치 A3-v0.2)을 사건 로그와 입력 로그 맨 앞에 남긴다.
  • 확인 대기 X1~X8: 확인 전에는 v0.3에 없는 제한을 넣지 않는다(구간·대상·예약 선택지 비활성 조건). 실행에 꼭 필요한 X1·X3 임시 기본값(라운드 종료 소멸)은 설정 한 곳에 두고, 적용될 때 사건 로그에 PENDING item=X1 …처럼 남긴다(10절 문법). 이 설정값을 사건 로그와 입력 로그 머리에 기록한다.

4. 흐름과 호출

상태: WaitingForPlan → Pre → BossAttack → WaitingForReserve(예약이 있고 E가 살아 있을 때만) → Post → RoundEnd → 다음 라운드 WaitingForPlan. 끝 상태는 Victory·Defeat.

  • 필요한 호출(이름은 ②가 정한다): 전투 시작(시작 상태), 의도 조회, 계획 제출(검증 결과: 오류 목록·조건부 안내 목록), 보스 공격 시작, 전투 시계 진행(ms), 정밀 입력 제출(공격 기준 ms), 예약 선택지 조회(각 후보의 유효 여부·이유·예상 효과), 예약 선택 제출, 일시정지·재개, 재도전.
  • 선행·후행 행동은 규칙상 즉시 처리한다. 연출 시간은 M2가 사건 사이에 둔다. 규칙에서 시간이 흐르는 구간은 보스 공격뿐이다.
  • 전투 시계: 진행 호출 한 번에 최대 50ms(기술 상한). 일시정지 중에는 진행하지 않는다. 보스 공격 시계는 M2가 선행 연출을 마치고 공격 시작을 알린 뒤부터 흐른다.
  • 진행 한 번은 [현재 시각, 새 시각) 구간을 시각 순서로 처리한다. 같은 시각에서는 예고 시작 → 누름(제출 순서) → 타격 판정·피해 → 공격 종료 순서로 처리한다. 새 시각과 같은 시각의 사건과 누름은 다음 진행에서 처리한다.
  • 누름이 어느 타격에 속하는지는 시각으로 정한다: 예고 시작 ≤ 시각 ≤ 타격 시각이면 그 타격의 누름이다. 예고 시작과 같은 시각의 누름은 그 타격의 첫 누름(이른 입력)이며, 뒤이은 누름으로 결과를 바꾸지 않는다.
  • 누름은 제출된 시각 그대로 판정하고 시각을 바꾸지 않는다. 제출 시각은 현재 시각 이상이어야 하며, 더 과거면 판정하지 않고 REJECTED_PAST로 기록한다(호출 계약 위반).
  • M2 호출 순서: 프레임마다 (1) 그 프레임에 들어온 누름을 현재 전투 시계 시각으로 제출하고 (2) 전투 시계를 진행한다. 누름 시각의 해상도는 프레임 간격이다(K1). 시험·재실행은 미래 시각의 누름을 미리 넣어 둘 수 있다.
  • 누름은 보스 공격 중이고 일시정지가 아닐 때만 판정 대상이다. 일시정지 중의 누름은 REJECTED_PAUSED, 공격이 끝날 때 남은 미래 누름은 무시로 기록한다. 보스 공격 밖의 누름은 M2가 걸러 M2 관찰 기록에만 남긴다. 예약 선택은 별도 호출로만 받는다.
  • 결정 지점은 예약이 있고, E가 살아 있고, 두 후보 중 하나 이상이 유효할 때만 연다. 두 후보가 모두 무효면 WaitingForReserve 없이 대기로 기록하고 후행으로 간다.

5. 기록 형식

  • 사건 로그: 한 줄에 사건 하나, R{라운드} {순번} {사건} 키=값 …. 필수 항목은 규칙 문서 13장이다. 실제 시각과 메모리 주소는 넣지 않는다. 정확한 문법은 ②가 U2에서 정해 이 절 끝에 적는다.
  • 입력 로그(저장 형식, JSON):

{
  "format": "celestiel.combat.input/2",
  "rules": "RT-v0.3+D8",
  "numbers": "A3-v0.2",
  "pending": { "X1": "roundEnd", "X3": "roundEnd" },
  "start": {
    "boss": { "hp": 450 },
    "party": [
      { "id": "A", "hp": 120, "focus": 3 }, { "id": "B", "hp": 80, "focus": 3 },
      { "id": "C", "hp": 80, "focus": 3 }, { "id": "D", "hp": 90, "focus": 3 },
      { "id": "E", "hp": 80, "focus": 3 }
    ]
  },
  "rounds": [
    {
      "round": 1,
      "plan": [
        { "actor": "A", "cmd": "A2" },
        { "actor": "B", "cmd": "B2", "phase": "pre", "order": 1, "target": "A" },
        { "actor": "E", "cmd": "RESERVE", "phase": "post", "order": 1, "heal": "A", "support": "D" },
        { "actor": "C", "cmd": "C2", "phase": "post", "order": 2, "link": "A" },
        { "actor": "D", "cmd": "D2", "phase": "post", "order": 3, "link": "C" }
      ],
      "attack": [
        { "call": "press", "clockMs": 800, "atMs": 800 },
        { "call": "pause", "clockMs": 1000 },
        { "call": "press", "clockMs": 1000, "atMs": 1000 },
        { "call": "resume", "clockMs": 1000 },
        { "call": "press", "clockMs": 1600, "atMs": 1600 }
      ],
      "reserve": "support"
    }
  ],
  "end": "retry"
}
  • attack은 그 라운드 보스 공격 중 규칙 핵심에 한 호출(누름·일시정지·재개)을 한 순서 그대로 적는다. clockMs는 호출할 때의 공격 시계 값, atMs는 누름에 붙여 넘긴 시각이다. M2의 실제 입력은 두 값이 같고, 시험처럼 미래 시각을 미리 넣으면 clockMs가 더 작으며, 계약 위반인 과거 시각 제출은 atMs가 더 작다. 거부·무시된 누름도 그대로 남는다.
  • 재실행기는 호출마다 시계를 clockMs까지 진행한 뒤(이미 그 시각이면 진행하지 않음) 같은 호출을 atMs 그대로 한다. 시계가 clockMs에 정확히 도달하지 못하면 원래 실행에서 나올 수 없는 기록이므로 재실행 실패다(확정 형식 메모). 미리 넣은 누름도 기록된 호출 순서대로 대기열에 넣는다.
  • reserve는 heal·support·wait이며 결정 지점이 없으면 뺀다. link는 릴레이 입력을 받을 제공 인물이다. order는 구간 안에서 1부터 겹치지 않게 매긴다. end는 retry 또는 none이다.
  • stopAtMs(선택, U7 총괄 승인): 재도전이나 기록 끝이 그 라운드 보스 공격 도중(일시정지 중 포함)이면 그때의 공격 시계를 attack 뒤에 적는다. 재실행기는 기록한 호출 뒤 그 시각까지만 진행하고 멈춘 채 end를 적용한다. 공격이 끝난 뒤(결정 지점 포함)의 재도전에는 적지 않는다.
  • pending은 확인 대기 항목의 임시 기본값이다. 값이 다르면 다른 규칙 조건으로 보고 재실행 비교 대상에서 뺀다.
  • start.participants(선택, TUT-PLAY-1, 규칙 문서 16장): 참가 인물 ID 배열(A→E 순서, 1~5명), 예 "participants": [ "A" ]. 5명 전원이면 쓰지 않고, 칸이 없으면 5명 전원으로 읽는다. 그래서 5인 기록은 이 칸이 생기기 전과 글자가 같고 형식 이름도 /2 그대로다. party는 계속 A~E 5명 모두의 시작 값을 적으며 참가하지 않은 인물의 값은 쓰지 않는다. 값 검증(빈 배열·중복·A~E 밖·순서 어긋남 거절)은 전투 시작이 하므로, 그런 기록은 재실행에서 시작 상태 오류로 실패한다. start 안 키 순서는 boss party participants다.
  • 파일: 시나리오를 실행한 테스트가 (내부 경로)과 <시나리오>.log를 쓴다(git 제외 폴더).
  • 재실행: 입력 로그만으로 같은 사건 로그를 글자 단위까지 똑같이 만든다.
  • 확정 형식 메모(U6, ② 작성, 2026-09-24). 코드: Source/Celestiel/Combat/CombatInputLog.*(JSON), CombatSession.*(기록), CombatReplay.*(재실행).
  • 머리에 "attempt"(그 로그가 시작하는 시도 번호, 1부터)를 둔다(총괄 허용). 없으면 1로 읽는다. 머리 키 순서는 format rules numbers pending attempt start rounds end, 라운드 키 순서는 round plan attack stopAtMs reserve다.
  • 기록하는 호출: 받은 계획(낸 순서 그대로), 보스 공격 시작(그 라운드에 attack 칸이 있으면 시작한 것이며 누름이 없으면 빈 배열), 공격 중 누름(보스 공격 밖이라 받지 않은 누름은 빼고, 거부된 누름은 넣는다)·받아들인 일시정지·재개, 받은 예약 선택, 재도전(end: retry). 시계 진행은 적지 않는다. 보스 공격이 진행 중인 동안(일시정지 포함) 기록기는 그 라운드의 stopAtMs를 지금 공격 시계로 두고 공격이 끝나면 지운다. 그래서 공격 도중의 재도전이나 그때 꺼낸 입력 로그(end: none)에만 stopAtMs가 남는다(U7).
  • 계획 항목: 대응 스킬(A2)은 예시처럼 phase를 적지 않고, 읽을 때 phase가 없는 스킬은 대응으로 본다. order는 0보다 클 때만, target·link는 있을 때만 적는다. 예약은 phase order heal support를 모두 적는다.
  • 재실행: 시작 상태로 시작해 attempt − 1번 재도전한 뒤 라운드를 차례로 돌린다. 기록한 공격 중 호출이 끝나면 stopAtMs가 있으면 그 시각까지만, 없으면 보스 공격이 끝날 때까지 한 번에 50ms씩 진행하고, reserve가 있으면 낸다. end가 retry면 마지막에 재도전한다. 결과 사건 로그는 그 시도 전체이고, retry로 끝나면 재도전 직후 새 시도의 첫 사건(머리·시작 상태·1라운드 의도)을 이어 붙인다. 보고 시나리오의 .log도 같은 범위다.
  • format·rules·numbers가 다르거나 원래 실행에서 나올 수 없는 기록이면 재실행 실패로 알린다(CP5 수정). 나올 수 없는 기록은 거부되는 계획·예약 선택, 공격 중 호출의 clockMs에 정확히 도달하지 못함(이미 지남·일시정지로 시계가 멈춤·그 전에 공격이 끝남), 거부되는 일시정지·재개, 보스 공격 밖의 누름, 보스 공격을 시작하지 않은 라운드의 공격 중 호출(JSON으로는 쓸 수 없고 메모리 입력 로그에서만 생김)이다. U7에서 stopAtMs에 정확히 도달하지 못함, stopAtMs 없이 일시정지로 멈춘 채 끝남, 보스 공격을 시작하지 않은 라운드의 stopAtMs를 더했다. stopAtMs 뒤에 라운드나 reserve가 더 있으면 앞의 라운드·예약 선택 검사에서 실패한다. 오류에는 위치와 이유를 적는다(예: rounds[0].attack[1]: resume clockMs 900에 도달할 수 없음(일시정지로 시계가 800에 멈춤)). 사건 로그에 남는 누름 거부(REJECTED_PAST·REJECTED_PAUSED)는 원래 실행에서도 나오는 정상 기록이므로 실패가 아니며 그대로 재현한다. pending이 다르면 재실행하지 않고 비교에서 뺀다.
  • 재도전 지점(U7): 보스 공격 도중·일시정지 중의 재도전은 stopAtMs로, 결정 지점의 재도전은 stopAtMs 없이(재실행이 공격 끝까지 진행하면 결정 지점이 다시 열린다) 원래 사건 로그 그대로 재현된다. 라운드 사이의 재도전은 U6과 같다. 자동 테스트 Celestiel.Combat.Replay.RetryDuringRound.
  • 조건부 미리보기 메모(U7, ② 작성, 2026-09-24). 코드: Source/Celestiel/Combat/CombatPreview.*. 규칙 14장·D5.
  • 호출: 계획 단계(WaitingForPlan)에서 CombatPreview::Build(전투, 계획). 전투를 복사해 계획 검증과 선행을 한 번 하고, 시나리오마다 그 상태를 다시 복사해 보스 공격 → 누름 → 예약 선택을 실행과 같은 호출로 이번 라운드 끝(라운드 종료 또는 승패)까지 돌린다. 실제 전투의 상태와 사건 로그는 바꾸지 않는다. 계획이 거부되면(계획 단계가 아닐 때 포함) 시나리오 없이 검증 결과만 돌려준다.
  • 시나리오: 예약이 있으면 무입력+회복, 무입력+공격 지원, 두 타격 성공+회복, 두 타격 성공+공격 지원 네 개다. 예약이 없으면 E 분기 없이 무입력, 두 타격 성공 두 개이고 예약 가정은 없음이다(규칙 14장, 총괄 결정). 준비 방어도 없으면 두 타격 성공은 NoReadyDefense라 결과는 무입력 하나다. 두 타격 성공은 타격마다 성공창 시작 시각에 미리 누른 것으로 계산한다. 예약 대기와 한 타격만 성공하는 두 순서는 넣지 않는다.
  • 결과마다 가정(입력 결과, 예약 선택과 그 대상 또는 없음), 확정 결과가 아니라는 표시(bEstimate, 늘 참), 결과값(끝 상태, 표적·A 체력, 보스 체력, 생긴 G·M·M+와 소비한 행동, 선행을 포함한 행동별 보스 피해의 기본·연계·지원·합계)을 담는다.
  • 없는 시나리오의 이유는 둘이다: NoReadyDefense(표적이 준비 방어를 고르지 않아 두 타격 성공 없음, 계획만으로 정한다), OptionInvalid(결정 지점에서 그 후보가 무효, 이유 target_down·focus_insufficient, 예약한 인물이 쓰러졌으면 actor_down). 두 후보가 모두 무효라 메뉴 없이 대기하면 사건 RESERVE_OPTION의 이유를, 예약한 인물이 쓰러져 메뉴 없이 취소하면 ACTION_CANCEL cmd=RESERVE reason=actor_down을 보고 정한다. 없는 시나리오에는 결과값이 없다.
  • 결정 지점 전에 승패로 끝나면(선행에서 승리, 공격 중 전멸) 없는 시나리오가 아니라 그 결과를 보인다. 예약 가정은 적용되지 않는다. 예약 판정(자동 대기·취소)이 이미 난 뒤 후행에서 승패가 난 것은 이와 다르며, 그 분기는 OptionInvalid다(CP6 수정). 승패로 남은 명령을 취소한 사건(reason=victory·defeat)은 예약 판정으로 보지 않는다.

10. 사건 로그 문법

U2~U5(② 작성, 2026-09-24). 코드: Source/Celestiel/Combat/CombatEvents.*, CombatBattle.cpp. 이 문법은 자동 테스트 Celestiel.Combat.Flow.LogGrammar가 글자 단위로 고정한다.

10.1 줄 형식

R{라운드} {순번} {사건} {키}={값} {키}={값} …

  • 라운드: 0은 전투 시작 머리, 1부터 라운드. 순번은 라운드 안에서 1부터 매기고 라운드가 바뀌면 다시 1이다.
  • 재도전하면 로그를 처음부터 새로 쓴다. 몇 번째 시도인지는 머리의 attempt에 있다. 재도전이 들어간 보고 시나리오의 .log와 재실행 결과는 끝난 시도의 로그 뒤에 새 시도의 로그(R0 1 BATTLE_START … attempt=N부터)를 이어 붙인다(5절 확정 형식 메모). 보스 공격 도중에 재도전하면 끝난 시도의 로그는 공격 도중에서 끝난다(ATTACK_END 없음, 5절 stopAtMs).
  • 키=값은 넣은 순서대로 나오고, 값에는 공백이 없다. 줄마다 LF로 끝난다. 실제 시각·메모리 주소·부동소수는 넣지 않는다.
  • 값 형식: 정수는 10진수, 바뀐 값은 이전>이후, 현재와 최대는 값/최대, 참·거짓은 true·false, 율은 1/10000 정수, 성공창은 시작-끝(양끝 포함, 입력창이 없으면 none)이다.
  • 시각(U3): atMs는 그 라운드 보스 공격 시계(ms)다. 누름·거부 사건에서는 누름에 붙어 온 시각이고, 그 밖의 사건에서는 처리한 시각이다. clockMs는 호출할 때의 공격 시계, hitMs는 타격 시각이다.
  • ID: 인물 A~E, 보스 boss, 스킬 A1~E3, 명령 WAIT·RESERVE, 예약 선택 heal·support·wait, 구간 pre·response·post, 효과 shield·support·G·M·MP(M+), 공격 R{라운드}.T01R, 타격 R{라운드}.T01R.H1·.H2(어느 타격에도 속하지 않는 누름은 none). link는 릴레이 입력을 받을 제공 인물이다.

ROUND_END라운드 종료(뒤에 EFFECT_EXPIRE·PENDING)—
  • VICTORY·DEFEAT 바로 뒤에 남은 명령의 ACTION_CANCEL이 실행 순서(선행 → 대응 → 후행)로 온다. 전멸로 끝나면 남은 타격·누름·ATTACK_END·G 결과는 기록하지 않는다.
  • 검증에서 거부된 계획은 로그에 남기지 않고 호출 결과로만 돌려준다. 릴레이 연결 검증(U4)의 오류 코드는 link_no_input·link_no_output·link_type_mismatch·link_cycle·link_future·link_duplicate이고, 조건부 연결 안내 link_conditional도 결과로만 돌려준다. 예약(U5)은 E가 아니면 reserve_not_allowed, 예약에 연결하면 link_no_input(예약이 입력을 받음)·link_no_output(예약의 출력을 받음)이다. 결정 지점에서 무효 후보를 고르면 거부하고 로그를 남기지 않는다.
  • PENDING은 규칙 문서의 'PENDING X1' 표기를 키=값 문법에 맞춰 PENDING item=X1 …로 적는다. applied=expired는 라운드 종료 소멸, applied=not_consumed는 피해 없는 행동이 공격 지원을 소비하지 않은 경우(X3)다.
  • HIT의 prec는 정밀 성공한 타격만 2500이고 그 밖에는 0이다. BOSS_DAMAGE의 relay는 소비한 릴레이 입력의 강화량이다(C2가 G를 소비하면 10, D2가 M이면 20·MP면 40, 소비하지 않았으면 0).
  • 보스 공격 순서(U3): ATTACK_START 뒤의 사건은 공격 시계 순서다. 같은 시각에서는 예고 시작(DEFENSE_ON·TELEGRAPH) → 누름(PRESS, 제출 순서. 판정에 쓴 첫 누름이면 바로 뒤 JUDGE) → 타격(JUDGE result=no_input·HIT·DOWN) → 공격 종료(HIT_VOID, 남은 미래 누름의 PRESS, ATTACK_END, 그 뒤 G 결과) 순서다. PAUSE·RESUME·REJECTED_*는 호출한 때 바로 남는다.
  • 누름은 제출할 때가 아니라 공격 시계가 그 시각을 지날 때 기록한다. 그래서 미리 넣은 누름과 그때그때 넣은 누름, 진행 간격이 달라도 로그가 같다. 보스 공격 밖(시작 호출 전·끝난 뒤)의 누름은 받지 않고 기록하지 않는다(M2 관찰 기록).
  • PRESS의 result=judged는 그 타격의 첫 누름이라 판정에 쓴 것이다. ignored의 reason: not_first 같은 타격의 뒤 누름, outside 어느 타격의 예고 구간(예고 시작~타격 시각)에도 속하지 않음, no_window 입력창이 없는 타격(표적이 준비 방어를 고르지 않음), after_attack 공격이 끝날 때 남은 미래 누름.
  • G(U3)는 준비 방어가 켜진 공격에서만 결과를 남긴다. 두 타격 모두 success이고 공격이 끝날 때 방어한 인물이 살아 있으면 EFFECT_ADD effect=G, 아니면 EFFECT_FIZZLE(방어한 인물이 쓰러졌으면 target_down, 아니면 hit_failed)다. 남은 G는 라운드 종료 때 EFFECT_EXPIRE로 사라지며 승인 규칙이라 PENDING을 남기지 않는다. G는 연결한 C2가 소비한다(U4).
  • 릴레이(U4): 소비 행동의 줄은 ACTION_START → 릴레이 입력 소비(EFFECT_USE) 또는 RELAY_MISS → 공격 지원 소비(EFFECT_USE effect=support) → BOSS_DAMAGE → 출력(EFFECT_ADD effect=M·MP) 순서다. C2는 연결이 없거나 G가 없어도 M을 낸다. 출력은 명시적으로 연결한 소비 행동만 쓰고, 쓰지 않은 출력은 라운드 종료 때 EFFECT_EXPIRE로 사라지며 PENDING을 남기지 않는다. 승리로 끝난 행동은 출력을 내지 않는다.
  • RELAY_MISS의 reason: provider_canceled 제공 행동이 취소됨(예: 제공자가 행동 전에 전투불능), provider_down 제공 행동은 했지만 출력이 생기기 전에 제공자가 쓰러짐(예: A2를 켠 A가 연타 중 전투불능), not_generated 제공자는 살아 있지만 출력 조건을 채우지 못함(예: 두 타격 성공 실패). 둘 이상 해당하면 이 순서로 앞의 것을 쓴다.
  • 예약(U5): 결정 지점은 보스 공격이 끝난 뒤(G 결과 다음) 후행 전에 한 번 연다. 예약한 E가 쓰러져 있으면 선택지 없이 ACTION_CANCEL cmd=RESERVE reason=actor_down, 아니면 RESERVE_OPTION 세 줄 뒤 RESERVE_OPEN(선택 대기) 또는 RESERVE_AUTO_WAIT(두 후보 무효)가 온다. 선택하면 RESERVE_CHOICE 뒤 PHASE phase=post로 이어 간다. 결정 지점에서는 전투 시계가 멈춰 있고 누름을 받지 않는다(기록도 없음).
  • RESERVE_OPTION의 유효 여부는 v0.3 조건(대상 생존·자원)과 D8만 본다. hp·heal은 대상의 현재 체력과 최대 체력까지의 예상 회복량(가득이면 0, 확인 대기 X5라 비활성하지 않음), bonus는 공격 지원 피해, later는 예약 자리 뒤에 남은 대상의 이번 라운드 공격(없으면 none = '이번 라운드 이후 공격 없음', 확인 대기 X4라 비활성하지 않음)이다.
  • 고른 회복·공격 지원은 E의 후행 자리에서 E2·E3 행동으로 ACTION_START(비용 한 번)부터 기록한다. 그 행동이 시작될 때 대상·자원을 다시 확인해 무효면 ACTION_CANCEL(재조준 없음)이다. 대기(선택·자동)는 그 자리에 기록이 없다.
  • 조건부 미리보기(U7)는 복사한 전투에서 돌리므로 실제 사건 로그에 사건을 남기지 않는다. 미리보기 값은 그 복사본의 상태와 사건(BOSS_DAMAGE, 릴레이 EFFECT_ADD·EFFECT_USE, 두 후보 무효 때의 RESERVE_OPTION, 예약한 인물 전투불능 때의 ACTION_CANCEL cmd=RESERVE reason=actor_down)에서 읽는다.

10.4 넓히는 규칙

U3~U6은 사건과 키를 더한다(예: 예고·입력창·누름·판정, 릴레이 생성·소비·불발, 예약 후보·선택). 이미 있는 키의 뜻과 순서는 바꾸지 않고 새 키는 뒤에 붙인다. 바꿔야 하면 이 절과 LogGrammar 기대값을 함께 고친다.
