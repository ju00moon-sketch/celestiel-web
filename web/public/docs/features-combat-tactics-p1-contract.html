0. 공통 원칙

항목정한 것
두 모드'이동 없음' 모드는 지금 규칙(RT-v0.3+D8) 그대로다. 시작 상태에 전술 정보가 없으면 이 모드이고, 입력 로그 v2는 늘 이 모드로 재실행한다. S1~S4는 이 모드에서 지금 기록과 바이트 단위로 같아야 한다. 새 규칙(위치·누구나 패링·다섯 명 준비 방어·무작위 키·회피·막기·치명타·엄호·경직)은 전술 모드에서만 돈다
좌표전투 공간 로컬, cm 정수(int32), 평면 X·Y. 원점 = 전투 공간 중심, +X = 파티 쪽 → 보스 쪽, +Y = +X를 볼 때 오른쪽[결정, ⑥ 배치안 2장]. 높이는 규칙에 없다(바닥은 평면)
방향0이 아닌 정수 방향 벡터(FCombatDir{X,Y}, 크기 자유). 판정은 벡터로 하고, 로그·화면에는 요(0.01° 정수)를 곁들인다. 성분은 ±2 × 반지름 안이다(아래 '정수 범위')
정수 판정부동소수 없이 정수로 한다. 거리 비교는 제곱 거리(int64), 각도는 내적·외적의 정수 비교, 길이가 필요하면 정수 제곱근(내림), 새 점을 만들 때는 cm 반올림(0.5는 0에서 먼 쪽)이다. 계산 순서는 이 문서와 코드 주석에 고정한다
정수 범위[기준안, P2-01]바깥에서 들어오는 값(전투 공간 파일, 시작 상태, 입력 로그 v3, 계획의 이동 목표, UI 조회 점)은 이 범위 안이어야 한다. 전투 공간 반지름은 1~4000cm다. 좌표(보스·인물 자리, 장애물 중심·꼭짓점, 이동 목표·조회 점)와 방향 벡터 성분은 ±2 × 반지름이다. 장애물 반지름·반폭과 몸·보스 반지름은 1~2000cm, 규칙 세트의 거리(이동 거리·사거리·엄호·연계, 패턴 반지름·길이·폭)는 1~8000cm다. 범위 밖이면 읽기·시작·계획 검증에서 정해진 오류(arena_radius·arena_range·arena_obstacle_size·start_tactics_body·start_tactics_boss·move_outside_arena·tactics_*)로 거절하고 그 값으로 기하를 계산하지 않는다. 경계 판정도 곱하기 전에 성분 범위를 먼저 본다. 이 범위에서 계산으로 생기는 점(넓힌 꼭짓점·띠와 부채 끝·강제 이동·보스 이동 자리)의 성분은 ±12,500 안이고, 두 점 차 성분 S ≤ 25,000에서 가장 큰 중간값(구역 판정 4(F·V)² ≤ 16S⁴ ≈ 6.3 × 10¹⁸)이 int64 안이다(CombatLimits 정적 검사)
두 가지 모양이동(자리·경로·겹침·돌진 멈춤)은 넓힌 다각형(2.4절)으로, 시야·공격 범위는 정확한 원·상자로 본다
결정적 난수무작위 키·치명타만 쓴다. CombatRandom::Roll(seed, attempt, round, stream, index): 입력을 64비트로 묶어 SplitMix64로 섞은 값이다. stream은 KEY·CRIT다. KEY는 index = 그 라운드 진짜 타격 번호(1부터), 키 = [Q, W, E, R, A, S, D, F]의 Roll mod 8번째(같은 키가 이어질 수 있다). CRIT는 index = 인물 번호(A=0~E=4)라 행동 순서를 바꿔도 누가 치명타를 받는지 옮길 수 없다. 시드는 시작 상태에 있고 입력 로그 v3에 남는다
기록 재현같은 규칙 세트·전투 공간·시드·계획·입력이면 사건 로그가 바이트 단위로 같다. 30·60fps에서 판정이 같다(입력은 지금처럼 보스 공격 시계 ms로 넣는다)
확인 대기사양 밖이라 총괄이 정한 기본값은 지금 X1·X3처럼 '확인 대기' 값으로 사건 로그 머리와 입력 로그 pending에 남긴다. 값은 규칙 세트 한 곳에서 바꾼다(3.4절 CT1·CT2)
UIUI는 규칙 계층이 낸 결과(이동 결과·미리보기·확정 공격·사건)만 그린다. 거리·가림·범위·구역·예고 시각을 UI가 따로 계산하지 않는다. 사건 필드의 이름·값 형식은 6.6절 표로 고정한다

2. K-T2 이동 명령과 결과

2.1 명령

  • FCombatCommand에 TOptional<FCombatPoint> MoveTo를 더한다. 없으면 제자리다. 이동은 행동과 따로 라운드마다 한 번이다[사양].
  • 입력 로그 v3 계획 항목에는 "move": {"x": …, "y": …}로 남는다.
  • '이동 없음' 모드에서 MoveTo가 있으면 계획 오류 NotInThisMode다.

2.2 해석(계획을 받을 때 한 번, 결과는 선행 시작 때 5인 동시 이동으로 보인다)

  1. 이동하지 않는 인물(명령에 MoveTo 없음)의 자리를 먼저 확정한다.
  2. 이동하는 인물을 이동 우선순위 순으로 하나씩 확정한다. 우선순위는 행동 실행 순서다[결정 Q1].
  • 순서: 선행(order 순) → 대응(준비 방어) → 후행(order 순, 예약 자리 포함) → 대기
  • 같은 칸 안에서는 A→E
  1. 목표는 계획 검증에서 이미 유효하다(아래 오류 코드). 이미 확정된 몸과 겹치지 않으면 그 자리다(Moved). 겹치면 [사양] "가장 가까운 빈 자리"로 옮긴다(Relocated).
  • 빈 자리 찾기[기준안]: 목표를 중심으로 반지름 10cm, 20cm, … 이동 거리까지 넓히는 고리마다 +X에서 반시계 16방향 후보(2.4절 방향 표 × 고리 반지름 ÷ 10000, cm 반올림)를 보고, 빈 자리(2.4절)이고 경로 길이 ≤ 이동 거리인 첫 후보를 쓴다.
  • 후보가 없으면 제자리다(Stayed, 이유 NoFreeSpot).
  1. 경로[결정 Q2]
  • 막는 것: 이동을 막는 장애물, 보스 몸, 움직이지 않는 인물의 몸(모두 넓힌 다각형, 2.4절). 움직이는 인물끼리는 도착 자리 겹침만 푼다.
  • 넓힌 다각형 꼭짓점을 잇는 최단 경로를 구한다. 길이는 선분 길이(정수 제곱근 내림)의 합이다. 선분은 다각형 변·꼭짓점에 닿아도 되고 안쪽을 지나면 안 된다.
  • 길이가 같은 경로는 꼭짓점 번호(장애물 순서 → 꼭짓점 번호)가 작은 쪽을 고른다.

2.3 결과


enum class ECombatMoveStatus : uint8 { Stayed, Moved, Relocated };
enum class ECombatMoveIssue  : uint8 { None, OutOfRange, Blocked, OutsideArena, NoPath, NoFreeSpot, NotAllowed };
struct FCombatMoveResult {
	ECombatActor Actor; FCombatPoint From; TOptional<FCombatPoint> Requested; FCombatPoint To;
	int32 PathLengthCm = 0; TArray<FCombatPoint> Path;     // From → 꼭짓점 → To(표시용). Stayed면 [From]
	ECombatMoveStatus Status; ECombatMoveIssue Issue;       // Relocated면 Issue는 None, 요청 자리가 겹쳤다는 뜻
	TOptional<FCombatPoint> BlockedAt; FString BlockedBy;   // 막힌 지점과 원인(장애물 id·"boss"·"edge"·인물 id)
};
  • BlockedAt
  • Blocked·OutsideArena·NoPath: 목표 자리다.
  • OutOfRange: 최단 경로에서 이동 거리만큼 간 점, 곧 갈 수 있는 끝이다.
  • 계획 검증(새 오류 코드): 목표에 도달할 수 없으면 계획을 받지 않는다.
  • MoveOutOfRange, MoveBlocked(목표가 장애물·보스 몸·움직이지 않는 인물 몸의 다각형 안), MoveOutsideArena, MoveNoPath, MoveNotAllowed(전투불능·참가하지 않음), NotInThisMode
  • 겹침으로 옮긴 것은 오류가 아니라 안내(MoveRelocated)다.
  • 가벼운 조회(끌기 중 UI용)
  • CombatTactics::QueryMove(const FCombatBattle&, const FCombatPlan&, ECombatActor, FCombatPoint) → FCombatMoveResult: 계획을 반영한 그 인물 혼자의 경로·도달 여부다.
  • 계획에 MoveTo가 없는 다른 인물은 지금 자리에서 경로와 도착을 막는다. MoveTo가 있는 다른 인물은 막지 않는다(Q2).
  • 움직이는 인물끼리의 겹침은 Build 결과(Relocated)로 안다.
  • 비용 목표[기준안]: 개발 빌드에서 한 번 0.5ms 이하다.
  • CombatTactics::ReachableCells(const FCombatBattle&, const FCombatPlan&, ECombatActor, int32 CellCm) → TArray<FCombatPoint>: 도달할 수 있는 칸의 중심 목록이다[②-B 요청 9].
  • 칸은 전투 공간 원점에 맞춘 격자다(중심 = (i × CellCm, j × CellCm)). 중심이 이동 원 안이고 QueryMove가 Moved인 칸만, Y 오름차순 → X 오름차순으로 준다.
  • CellCm은 25 이상, 전투 공간 지름(2 × radiusCm) 이하만 받는다(밖이면 빈 목록).
  • 비용 목표[기준안]: 개발 빌드에서 칸 50cm·이동 거리 800cm 한 번 5ms 이하다. UI는 선택 인물이나 계획이 바뀔 때만 부르고 캐시한다.
  • 사건 MOVE(6.6절): 계획을 받은 뒤 PLAN 줄들 다음에 A→E로 한 줄씩 남긴다.

2.4 몸·장애물 모양(이동용)[⑥ 요청 1, 기준안]

  • 방향 표: k × 22.5°(k = 0~15, +X에서 반시계)의 (cos, sin) × 10000을 반올림한 정수 16쌍이다.
  • 넓힌 원(반지름 R = 원래 반지름 + 움직이는 몸 반지름): 외접 16각형이다.
  • 꼭짓점 반지름 Rv(R) = ⌈R × 1,000,000 ÷ 980,785⌉ + 1(1/cos 11.25°를 올림한 외접 반지름에 여유 1cm)
  • 꼭짓점 k = 중심 + 반올림(Rv × 표 k ÷ 10000)
  • 다각형은 반지름 R 원을 늘 덮는다(변까지 거리 ≥ Rv × cos 11.25° − 0.72 > R). 예: 기둥 90 + 인물 42 → R 132, Rv 136이고, 인물 몸과 기둥 메시 사이는 1.4~4cm 남는다.
  • 넓힌 상자: 상자 네 꼭짓점마다 움직이는 몸 반지름의 외접 16각형을 놓은 볼록 껍질이다.
  • 경계: 정확한 원이다. 몸 전체가 안 = X² + Y² ≤ (radiusCm − 몸 반지름)². 원은 볼록하므로 안쪽 두 점을 잇는 선분은 늘 안쪽이다. 그래서 경로는 경계 밖 꼭짓점만 빼면 된다(초안의 64각형은 뺐다).
  • 빈 자리: 경계 안이고, 이동을 막는 장애물·보스 몸·확정된 몸의 넓힌 다각형 안쪽(변 위는 밖)이 아닌 점이다.
  • 모든 자리(시작·이동·엄호 강제 이동·보스 이동)는 늘 빈 자리 조건을 지킨다. 그래서 경로 출발점은 다각형 밖이다. 다각형은 중심 대칭이라 "A가 B의 다각형 밖"과 "B가 A의 다각형 밖"은 같다.
  • 보스 몸 이동(돌진)은 같은 방식으로 장애물을 보스 반지름만큼 넓혀 본다(5.3절).
  • 시야·공격 범위 판정은 이 다각형이 아니라 정확한 원·상자로 본다(5.1절, 6.3절).

3.3 검증·해시·패키지

  • 규칙 계층이 불러올 때 아래를 검증한다. 실패하면 전투를 시작하지 않고 이유를 돌려준다.
  • 형식(3.1절), id 중복 없음
  • 정수 범위(0절): 반지름 1~4000, 좌표·보스 방향 성분 ±2 × 반지름, 장애물 반지름·반폭 1~2000. 범위 밖 값은 읽는 자리에서 거절하고 그 값으로 계산하지 않는다(arena_radius·arena_range·arena_obstacle_size). 파일을 거치지 않은 시작 상태(시험·입력 로그)도 전투 시작 때 같은 검사를 거친다
  • 시작 자리: 경계 안, 서로·장애물·보스 몸과 겹치지 않음(2.4절 빈 자리와 같은 다각형)
  • corners가 중심·반폭·요와 ±1cm
  • 해시: 파일 바이트의 SHA-256 앞 16자다. 입력 로그 v3 머리에 남긴다. 재실행 때 다르면 ArenaMismatch로 비교에서 뺀다(확인 대기 값이 다를 때와 같은 방식).
  • 패키지: JSON은 에셋이 아니라서 스테이징 설정이 필요하다. DefaultGame.ini의 +DirectoriesToAlwaysStageAsUFS=(Path="Data/Combat")이고, CT-1에서 ②-A가 넣었다[결정 Q17·D4].

  • 예약은 후보마다 ReserveActions를 준다. 실행 때는 결정 지점의 자리·시야로 다시 본다.
  • 구역 경계 각은 FCombatTacticsRules::FlankFromDeg(60)·BackFromDeg(150)로 조회한다. 그리기용이다. 판정은 6.3절 정수 비교이고, 시제품에서 두 값은 고정이다(바꾸려면 판정 식도 바꾼다)[②-B 요청 8].
  • 조건부 미리보기 카드(기존 시나리오)는 유지한다[결정]. 위치를 반영해 계산하고, 구성은 지금과 같다: 무입력·두 타격 성공 × 예약 분기.
  • 전술 모드의 '성공' 가정은 영향받는 인물마다 자기 판정 폭 안 패링 '성공'이다(완벽 아님)[기준안].
  • 카드 밖 값(인물별 행동·연계)은 무입력 가정이다. 돌진은 맞는 경우라 보스 자리가 그대로이고, 빗나갔을 때 옮길 자리는 Attack.BossEndIfMissed로 따로 준다.
  • 행동 시점 보스 방향[결정 Q20]: 선행 행동은 보스가 돌기 전 방향, 후행 행동은 이번 공격에서 돈 뒤 방향이다.
  • 치명타 표시[결정 Q18]
  • 시나리오 체력 결과는 치명타가 없다고 보고 계산한다.
  • 피해 항목(FCombatPreviewDamage)마다 치명타일 때 피해(CritDamage)와 확률(CritChance)을 곁들인다. 화면에는 예를 들어 "피해 40 (치명타 60, 25%)"로 보인다.
  • 실제 굴림은 보이지 않는다. 굴림을 보이면 공정한 확률이 아니라 미리 알려 주는 값이 되고, 굴림이 시드·시도·라운드·인물에서 정해지므로 계획을 바꿔 가며 고를 수 있기 때문이다.
  • 무작위 키는 계획 화면 미리보기에 없다[결정]. 계획을 받을 때 공개한다(6.1절).
  • 계산은 규칙 계층의 실행 코드와 같은 함수를 쓴다(지금처럼 전투를 복사해 돌린다).
  • 성능 목표[기준안]: 개발 빌드에서 계획 한 번 미리보기 5ms 이하다(5인, 장애물 6개).

  • 박자
  • 타격 시각(ms) = FirstBeatMs + Beat × 60000 / Bpm(곱한 뒤 정수 나눗셈 내림)이다. 박 번호는 쉼(.)을 포함해 센다. [사양] '♩ ♩ . ♩' → 박 0·1·3. 같은 패턴은 늘 같은 박자다[사양].
  • 예고 시작(ms): 악보 첫 박은 타격 시각 − FirstTelegraphMs, 나머지 박(가짜 포함)은 타격 시각 − FollowUpTelegraphMs다(지금 T값). 데이터 검증: 첫 예고 시작 ≥ 0.
  • 두 시각은 의도·확정 공격에 박마다 들어 있다(5.4절). UI는 식을 다시 계산하지 않는다[②-B 요청 5].
  • 가짜 예비 동작은 FakeBeats 박에 예고만 보이고 타격이 없다. 가짜는 바로 다음 진짜 타격에 속한다. 그 타격은 가짜 예고가 시작될 때부터 입력을 받으므로, 가짜에 누르면 그 타격이 '너무 이른 입력'으로 실패한다[사양].
  • 조준 규칙(계획 시점 = 라운드 시작 때 의도를 만드는 순간의 자리)
  • NearestAtPlan: 계획 시점에 보스 중심과 가장 가까운 인물 쪽 방향으로 고정한다. 같으면 A→E.
  • FarthestAtPlan: 계획 시점에 가장 먼 인물 Count명의 자리에 원을 고정한다. 같으면 A→E. 살아 있는 참가자가 모자라면 원도 그만큼이다.
  • NearestAfterMove: 이동이 끝난 자리에서 가장 가까운 인물 쪽이다[사양 규칙 대상].
  • LowestHpRatio: 체력 비율 최저, 같으면 A→E(시제품에 없음).
  • 거리는 중심 거리 제곱으로 비교한다(인물 반지름이 모두 같아 가장자리 거리 순서와 같다).
  • 범위에 맞는 기준[결정 Q21]: 인물 몸(원)이 범위 모양과 겹치면 맞는다. 접하기만 하면 밖이다.
  • 모양은 정확한 원·부채·띠로 보고 정수로 판정한다. 부채 반각은 45°·90°만 받는다(정확한 정수 비교가 되는 각). 부채·직선의 끝점은 cm 반올림한 정수 점이다.
  • 전장(Arena)은 살아 있는 참가자 전원이다.
  • 모든 패턴의 공격 원점은 보스 중심이다[결정 Q26]. 엄호 강제 이동 방향과 막기 정면 판정이 이 점을 쓴다.
  • 순환[결정 Q14]: 규칙 세트의 순서표를 라운드 번호로 쓴다. 라운드 r은 표의 (r − 1) mod 길이 번째이고, 순환 번호는 (r − 1) ÷ 길이 + 1이다. 경직으로 공격이 취소돼도 밀리지 않는다[결정 Q26]. '회피 불가 연속 사용 금지'[사양]는 데이터 검증이 막는다.

5.3 돌진의 대가[결정 Q15·Q24]

  • 띠: 보스 중심이 공격 시작 자리에서 조준 방향으로 가는 선분(길이 LengthCm, CT2로 멈추면 그 점까지)이고 폭은 WidthCm이다.
  • 멈추는 점(CT2 stop): 보스 몸이 장애물(보스 반지름만큼 넓힌 다각형, 2.4절)이나 경계(radiusCm − 보스 반지름 원)에 처음 닿는 점이다. 정수 cm로 출발 쪽 내림이다. AREA의 end·stop에 보인다.
  • 빗나감: 띠에 몸이 걸린 인물이 없거나, 걸린 인물이 모두 회피에 성공했을 때다. 패링(완벽 포함)·막기는 빗나감이 아니다.
  • 빗나가면 공격이 끝날 때 보스가 띠 끝으로 옮기고 돌진 방향을 본다(BOSS_MOVE). 끝 자리가 인물 몸(넓힌 다각형)과 겹치면 겹치지 않을 때까지 출발 쪽으로 당긴다.
  • 맞으면 보스 자리는 그대로다(연출은 부딪힌 뒤 제자리로). 방향은 공격 시작 때 돈 그대로다.
  • 돌진 타격은 관통이라 엄호로 대신 받을 수 없다.
  • 미리보기는 빗나갔을 때 옮길 자리를 BossEndIfMissed로 준다.

6.1 반응 입력

  • 입력 문맥
  • 진행자는 보스 공격 동안 반응 입력 문맥(EBattleInputContext::React, 지금 PreciseDefense를 넓힌 것)을 켠다.
  • 이 문맥에서는 전략 조망 키(A·D·Q·E·Z·X)를 받지 않는다. 계획 중에는 반응 키를 받지 않는다.
  • 한 번에 하나의 입력 초점(RT-10)을 지킨다.
  • 막기 키는 물리 상태로 받는다(왼쪽·오른쪽 Shift 중 하나라도 누르면 막기). 보스 공격 시작 전부터 누르고 있었거나 정지 중에 바꿨으면, 반응 문맥이 켜진 첫 공격 프레임에 그 시각으로 block_down·block_up을 내 규칙 상태를 맞춘다(표시 로그 source=sync)[기준안].
  • 한 프레임에 받은 막기 누름·뗌은 받은 순서대로 모두 낸다. 규칙 막기 상태는 입력을 처리할 때(시계 진행) 바뀌므로, 같은 상태인지와 맞춤이 필요한지는 아직 처리하지 않은 막기 입력까지 반영한 FCombatBattle::IsBlockHeldAfterQueue()로 본다. 그 값과 같은 전이는 내지 않는다(표시 로그 reason=same_state)[기준안, P2-02].
  • 규칙 핵심 API: ECombatPressResult SubmitReaction(const FCombatReaction& In), FCombatReaction{ ECombatReactionKind Kind /*Parry·Dodge·BlockDown·BlockUp*/; ECombatReactKey Key /*패링만*/; int32 AtMs; }. 시계 계약(과거 시각 거부·정지 중 거부)은 지금과 같다. 지금의 SubmitPress는 '이동 없음' 모드에서 그대로 쓴다.
  • 막기 상태[②-B 요청 4]: 사건 REACT kind=block_down·block_up이 늘 나오고(6.6절), 조회 FCombatBattle::IsBlockHeld()가 있다. 실행 화면의 막기 칸은 둘 중 하나로 켠다.
  • 키 공개 시점[결정]
  • 이번 라운드 공격의 타격 키는 계획을 받는 순간(실행 시작) 모두 정해진다.
