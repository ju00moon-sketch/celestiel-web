2.1 이전 끈 분할 계약과 보존할 데이터 조건

아래 ID3/4·두 Groom 구성은 이전 연속 가닥 구조의 조건부 계약이다. 최신 X자 구조는 §2.2 대조 전까지 이 구성으로 확정하지 않는다. POLY·단위·ID/가이드·root UV·manifest의 보존 조건은 유지한다. 실제 수량은 승인 파일에서 측정하며 이전 guide 기본420을 완료 수량으로 쓰지 않는다.

  • POLY 곡선, root→tip 순서, 비순환. HGR 입력은 curve-domain INT groom_group_id, groom_guide(0/1), groom_id, FLOAT2 groom_root_uv, point-domain FLOAT radius(cm). ABC에서는 H3 규격의 groom_group_id·groom_guide·groom_root_uv와 widths 등을 대조한다. ABC width는 지름=2×radius다. 그룹 이름은 manifest에서 관리한다.
  • 분할 후 ID는 전체에서 고유하게 주고, manifest에 source_curve_id, 앞/뒤 새 ID, guide 여부, source 길이 구간, 절단점·접선·radius를 남긴다. 곡선 중간에 절단점을 삽입하면 그 위치/보간도 기록한다. 두 구간을 합친 중심선·굵기가 승인 원본과 같은지 수치와 확대 렌더로 검사한다. 가이드 감축·새 모양 생성은 하지 않는다.
  • 인계 manifest에는 그룹별 R/G/점 수, GroupID→각 Groom의 GroupIndex, root의 대상 메시 SHA·LOD·삼각형/삼각형 내 좌표·UV0, 본/pose 판, 좌표 변환, 끈 기준 transform을 넣는다. 두피 UV seam은 vertex UV 평균이 아닌 해당 root의 삼각형 UV로 정한다.
  • 바인딩 구현 제안: Main(ID0~3)은 Quinn 스킨 두피에, Ponytail(ID4)은 같은 pose의 작은 스킨 끈 기준면에 각각 Groom+Binding으로 연결한다. 끈 기준면은 실제 끈 위치에서 head를 추종하며 렌더에는 보이지 않는다. 포니테일 root를 가까운 실제 두피로 재투영하지 않는다. 별도 Groom 안에서는 ID4의 GroupIndex가0일 수 있어 원본 ID와 혼동하지 않는다. 두 컴포넌트 비용도 1.2ms 목표에 포함한다.
  • 위 끈 기준면은 이 분할 방식이 선택될 때 ④에게 필요한 인계 항목이다. 제안 이름 SK_FP_HairTieAnchor, 완전한 공통 뼈대·같은 reference pose·UV0·필요 LOD와 root 대응을 받는다. 최종 머리·두피 전에는 최종 자산 바인딩을 실행하지 않는다. §8.1의 별도 시험 입력을 쓰는 작은 Dev 시험은 구분한다. 기준면 없이 임의 두피 바인딩으로 대체하지 않는다.
  • groom_root_uv가 끈 기준면을 뜻하는 ID4는 색 조회 좌표와 구분한다. 원래 색 조회 좌표·끈 위치에서의 실제 색/폭을 manifest에 보존하고 승인 색 manifest에 맞춰 재질을 검증한다. 분할 때문에 root darkening이 다시 시작하거나 매듭에 색 띠가 생기면 해결 전 인계 통과로 보지 않는다.
  • 카드도 Main/포니테일 분리와 GroupIndex/LODIndex를 따라야 한다. 카드 메시·atlas 및 나침반·사슬·십자가·찢어진 리본은 ④ 원본, UE 연결·Chaos 설정은 ⑤ 담당이다. 장식 원본 제작 시점은 총괄의 후속 배정을 따른다.

현재 원본 좌표는 cm·+X정면·+Y인물 왼쪽, 예전 참조 exporter는 UE 변환 X,-Y,Z를 제안한다. H3의 작은 시험 X,Y,Z를 그대로 쓰지 않는다. 축 맵은 CU1에서 확정한 공통 Skeleton/두피의 로컬 축·비대칭 기준점과 대조해 한 번만 적용한다. 배우 정면+X와 스킨 메시 로컬 정면(+X 또는 엔진 마네킹의+Y)은 구분하고, CHAR-UE의 생성자 yaw 보정을 그룸에 중복 적용하지 않는다. 출력이 target mesh 로컬 좌표/UE cm라면 Groom Rotation0/Scale1로 시작하고 실제 길이·지름을 검증한다. 음수/비균일 객체 배율을 남기지 않는다.

4.2 UE 조립과 검증 순서

아래 Main/Ponytail 두 묶음의 이름·수는 이전 구조의 실행 예시다. 실제 최신 Groom 구성은 §2.2의 대응표를 확정한 뒤 치환하며, 예시를 근거로 원본을 분할하지 않는다.

  • 최초 자산은 /Game/Dev/HAIR2/: GR_FP_Hair_Main_Test·GR_FP_Hair_Ponytail_Test, 각각의 GB_ Binding, SK_FP_Scalp_Test·SK_FP_HairTieAnchor_Test, PA_FP_HairCollision_Test, M_FP_HairStrands_Test, 카드/장식 시험 자산. 최종 외형 승인 뒤 /Game/Art/Characters/FemaleProtagonist/Hair/로 인계한다. 지금 어느 자산도 생성하지 않는다.
  • 최신 X자 구조는 §2.3대로 G0~G5 한 Groom/스킨 두피부터 시험한다. 별도 G4가 필요한 경우에만 Main은 최종 두피, Ponytail은 X자 끝 기준면을 TargetSkeletalMesh로 GroomBindingType=SkeletalMesh 생성한다. 같은 면 위에 만든 Groom이면 SourceSkeletalMesh는 불필요; 다른 면→목표 면 변환 때만 source와 MatchingSection을 명시한다. NumInterpolationPoints는 설치본 기본값을 기록하고 시작한다. 원래 root 대상 삼각형인지 확인한다.
  • 다중 LOD마다 binding의 projection/root mapping을 검사한다. UV seam 부근 root UV는 삼각형/loop 기준으로 대조한다. 최초 조사 생성기의 vertex UV 평균은 현재 합격 기준이 아니다. 최신 출력의 barycentric root UV를 실제 대상 삼각형과 비교하고 이전 평균 결과와의 차이도 기록한다.
  • GroomComponent는 변형되는 두피 SkeletalMeshComponent에 붙여 BindingAsset을 지정한다. 단순 head socket 부착만 확인하고 Skinning Binding 성공이라고 하지 않는다. 두피가 몸 Leader Pose를 따르면 숨김 상태에서도 본 갱신과 Skin Cache가 유지되는지 검사한다. head에만100% 스킨된 두피라도 몸통 회전·목 동작 시 같은 transform 체인을 따라야 한다.
  • 기존 skeleton/physics를 변경하지 않고 캐릭터 뼈대와 맞는 전용 hair collision PhysicsAsset을 쓴다. Head 구/타원체 후보·neck capsule·양 어깨/상완·윗가슴/등 8~12개 단순 충돌체부터. 긴 머리 길이에 따라 spine 하단을 추가한다. target 두피에 필요한 spine/clavicle 본이 없으면 full-body component의 PhysicsAsset 공급 경로를 검증하거나 완전한 공통 뼈대 두피 인계를 받는다.
  • Collision Query/Gameplay는 비활성, 헤어/천/장식 전용. 메시 삼각형 전체 복잡 충돌로 대체하지 않는다. 망토가 생기면 몸 proxy와 망토 외형 사이의 실제 간격을 다시 확인한다.
  • 모발 재질: Hair/Main Strands 사용 표시, 모발 방향/roughness·색을 정면/역광에서 비교. Blender absorption 수치를 UE BaseColor에 직접 복사하지 않는다. Nanite 표시는 Groom에 필요하지 않다. Nanite를 쓰는 고정 장식 메시가 있으면 해당 부모 재질의 set_blockout_nanite_usage.py --check 포함 여부를 확인한다.
  • 슬롯: Groom Editor Materials+그룹 Rendering 연결→저장·재로드를 검증한다. Python에서 보호된 MaterialSlotName을 강제로 쓰지 않는다. 동일 Hair_Main을 공유하는 그룹도 GroupID/GroupIndex/SlotIndex 표를 남긴다. 카드 material slot은 별도로 확인한다.
